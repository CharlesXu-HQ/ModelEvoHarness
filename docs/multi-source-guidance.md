# Model-structure and experiment guidance from multiple sources

ModelEvoHarness uses [FunRec's pinned inventory](source-coverage.md) as its broad research map and retains the actual working explanations in [22 local technical guides](knowledge/README.md). This page explains what four other projects added to the map. The comparison is about **mechanisms and experiment design**, not model counts or leaderboard ranks. Detailed source analysis is in the [DeepCTR and Torch-RecHub review](research/deepctr-torch-rechub-review.md) and [RecBole and industrial recommendation review](research/recbole-wang-review.md).

## When to consider a structural change

A structural proposal should start with an observed weakness, state why the architecture might address it, and name a simpler controlled comparison. The 14 [machine-readable patterns](../src/model_evo_harness/data/structure_patterns.json) cover the existing and supplemental method cards. This is a set of **conditional hypotheses**, not an ordered upgrade path:

| Measured signal | Structure and its distinguishing feature | Evidence and first controlled test |
| --- | --- | --- |
| Popularity/content retrieval misses repeat-interest items. | Collaborative neighbors or compact user/item factors. | Check interaction density and cold slices; compare at fixed temporal split, catalog and top-K. |
| ID-only item vectors fail on new or sparse items. | Context-based item vectors, optionally blended with side attributes. | Check pre-decision context and attribute coverage; compare ID-only, context and shuffled-context controls. |
| A linear or plain MLP model has repeatable errors on supported field pairs. | FM-style factorized pair interactions, attention or field-pair weights such as FwFM. | Verify field identities, pair support and decision-time availability; ablate the interaction branch at fixed inputs and embedding width. |
| Pairwise terms leave stable higher-order residuals. | Wide crosses, DCN, DCNv2, xDeepFM or field attention encode different cross orders and parameterizations. | Keep fields and backbone fixed; compare one cross branch with its ablation and a pairwise baseline at a declared cost. |
| Candidate recall is low at a fixed top-K. | Two independently computable user/item towers allow indexed retrieval. | Freeze catalog, negatives and index freshness; compare against a simpler tower or collaborative retriever. |
| In-batch negatives distort retrieval by item popularity. | YouTubeSBC-style correction adjusts logits using item sampling weight. | Require actual sampler weights; compare corrected and uncorrected logits on identical batches and full-catalog evaluation. |
| Candidate-specific preferences are hidden by one pooled user history. | DIN/DIEN/DSIN condition history aggregation on the target, with evolution or session variants. | Use only events before each decision; compare against masked mean pooling, then ablate extra components. |
| Recent event order or current-session intent matters for next-item retrieval. | SASRec/SDM/HSTU model ordered history; NARM combines session context and local intent. | Require timestamps, session boundaries where relevant and a fixed candidate universe; compare with order-agnostic pooling. |
| One user vector misses several supported interest clusters. | MIND represents multiple interests. | Compare one versus multiple vectors with the same catalog, total K and deduplication rule. |
| Multiple observed tasks help one another unevenly. | Shared-bottom, MMoE or PLE vary how representations are shared and gated. | Define label coverage and task priorities; compare independent heads, shared bottom and one gated variant on the same rows. |
| A later outcome is sparse but truly follows an earlier labeled outcome. | ESMM imposes an ordered probability relation; AITM transfers representations along the observed outcome chain. | Verify task order and missingness; compare with independent heads and report later-stage and calibration metrics. Treatment assignment plus one outcome is not an ordered funnel. |
| A global model leaves stable scenario-specific residuals. | STAR/HMoE/PEPNet condition normalization or experts on a pre-decision scenario. | Check per-scenario support; compare a pooled model, scenario heads and one conditioned variant. |
| Context response differs but separate large models overfit or cost too much. | APG uses compact contextual adaptation; MLR mixes soft local linear functions. | Check segment support and serving cost; compare a global model and size-matched nonlinear or segment baselines. Learned regions are not causal effects. |
| Sorting independent item scores misses slate position effects. | PRM/PRS condition on slate context or position response. | Require logged candidate sets, positions and a valid slate evaluator; reorder the same feasible candidates and compare slate-level outcomes. |

Separate [supplemental families](../src/model_evo_harness/data/supplemental_families.json) cover soft segmentation, prediction-to-decision mapping, and typed knowledge-graph retrieval. For the graph case, require item–entity links, typed triples, catalog and time cutoff; compare against a matched non-KG retriever. Prediction-to-decision mapping is **not a neural architecture change**: freeze predictions and compare action rules under the declared objective.

The machine-readable [structure patterns](../src/model_evo_harness/data/structure_patterns.json) give the Agent a structural change, a symptom that justifies trying it, required evidence, a control and a rejection signal. A pattern links to one or more method cards; `ready` only means input capabilities were declared. The Agent must cite the task result and propose a falsifiable ablation. All 44 cards have original PyTorch and TensorFlow [model references](models.md), with exact paths in the implementation manifest. The generic TwoTower structure is not a method card. A framework implementation is never evidence of task-level gain.

## What the harness checks

The Agent receives the catalog, task snapshot, family/method applicability and relevant decision checks. The host may include an optional `feature_schema` and `evaluation_protocol` in its snapshot. The protocol should identify the unit, fixed split and metric, plus candidate universe, full or sampled evaluation, negative source, cutoff, preprocessing and top-K where applicable. The harness fingerprints it and refuses to resume a run under a changed protocol; the host still performs actual evaluation and keeps the final holdout isolated. See the [adapter contract](adapter-contract.md).

Decision checks ask whether inputs were available before the decision, whether a negative is observed or sampled, whether full-catalog and sampled metrics are being confused, and whether the bottleneck lies in the predictor or its action rule. For a decision-rule experiment, freeze predictions and compare rules under the task's declared objective and constraints. If shared budgets or traffic cause interference, record the risk and require a separate online validation design; an offline row-wise score cannot resolve it.

## Training and feature evidence

The [training patterns](../src/model_evo_harness/data/training_patterns.json) make loss choice, pairwise/listwise objectives, hard-negative mining, hard-example weighting, class balancing, optimizer schedules, clipping, regularization, calibration and time-safe augmentation eligible experiment directions. Each needs its own measured symptom, required data contract, fixed control and rejection condition. The [loss guide](../src/model_evo_harness/knowledge/training_objectives.md), [hard-example guide](../src/model_evo_harness/knowledge/sampling_and_hard_examples.md) and [training controls](../src/model_evo_harness/knowledge/optimization_and_regularization.md) contain the local technical reasoning. A hard negative is not simply any low-response user in a randomized coupon experiment; its definition must match the sampling and label process.

A weak result usually calls for more experiments with existing decision-time fields. After two completed trials with distinct mechanisms, the Agent can leave a specific `future_feature_suggestions` record while continuing. A terminal `request_data` also requires those trials and evidence that the missing signal blocks progress, or an explicit host-supplied `domain_requirements` item that names a business prerequisite, source and timing. The latter permits an immediate human request or suggestion when, for example, the objective requires a coupon-cost field that the host knows is absent. See the [feature-gap guide](../src/model_evo_harness/knowledge/feature_gap_decisions.md) and [adapter contract](adapter-contract.md).

Reflections keep **technical experience** about tested mechanisms separate from **business experience** about observed user or policy response. The latter must cite a host `business_observations` ID with population, metric, estimate and uncertainty; without one it is `not_observable`. The [business insight guide](../src/model_evo_harness/knowledge/business_insight_synthesis.md) explains the inference boundary. Both experience types are scoped to the frozen task, dataset and protocol.

## Deferred and bounded ideas

- We did not add duplicate cards for architecture names already covered by FunRec. All 44 method cards have independently written [PyTorch and TensorFlow references](models.md), with explicit simplification boundaries. The task adapter still owns training, feature processing, losses and evaluation.
- Additional field-aware, convolutional or sequence variants remain task-specific. In particular, a convolution over fields needs a meaningful field order; [FGCNN's source](https://github.com/shenweichen/DeepCTR/blob/1b5fe40e158d1ee6af8b1d9df217a5ed5aea9136/deepctr/models/fgcnn.py) alone does not establish one.
- Generative or semantic-item retrieval requires item–token alignment, legal-ID decoding and a defined catalog and cost budget. The existing FunRec families cover the direction, while [Torch-RecHub's generative models](https://github.com/datawhalechina/torch-rechub/blob/beb8b46fb718ce486ea5feb6847ac3abf0c491d4/docs/en/models/generative.md) illustrate implementation contracts; no generative adapter is bundled.
- Lecture examples about traffic allocation, A/B interference or hard slate constraints do not become offline gains on a fixed coupon dataset. A single binary coupon action has no session, item catalog or slate merely because a library offers those models.

The local guides, training patterns and model references do not assert that any architecture improved a task metric. No external project's code or prose is copied into this Apache-2.0 package.
