# Model structure and training audit — 2026-10-05

## What was checked

This review compares the working tree of ModelEvoHarness with the public, first-party [FunRec table of contents](https://github.com/datawhalechina/fun-rec/blob/master/README_en.md), [FunRec model/training source](https://github.com/datawhalechina/fun-rec/tree/master/src/funrec), [DeepCTR exported model list](https://github.com/shenweichen/DeepCTR/blob/master/deepctr/models/__init__.py) and [feature explanations](https://deepctr-doc.readthedocs.io/en/latest/Features.html), and [Torch-RecHub model list and trainer layout](https://github.com/datawhalechina/torch-rechub/blob/main/README.md). The upstream public pages were checked on 2026-10-05. This is a mechanism/protocol audit, not a performance benchmark or an assertion that the upstream projects themselves are error-free.

The local catalog has **22 families, 44 method cards, 90 implementation entries** (44 cards × PyTorch/TensorFlow plus generic TwoTower in both), and 13 training patterns. `coverage_report()` finds no missing paths **against the pinned FunRec inventory** at [`upstream_inventory.json`](../../src/model_evo_harness/data/upstream_inventory.json#L1); it compares path sets, not model behavior or the current upstream branch ([implementation](../../src/model_evo_harness/catalog.py#L227)). These three levels must stay separate:

1. **Method card:** a hypothesis, prerequisites and proposed comparison, e.g. [`method_cards.json`](../../src/model_evo_harness/data/method_cards.json).
2. **Mechanism reference:** importable direct-framework forward/scoring code, now bounded per entry by [`model_implementations.json`](../../src/model_evo_harness/data/model_implementations.json). It is not automatically paper-equivalent.
3. **Training protocol:** row/label construction, preprocessing, loss, negatives, optimization budget, validation, uncertainty and decision rule. The harness intentionally delegates this to the host ([adapter contract](../adapter-contract.md#L3)); the manifest alone is not an executable protocol.

I checked the PyTorch and TensorFlow model modules, the manifest, [training helpers](../../src/model_evo_harness/models/pytorch/training.py#L1), [Agent instructions](../../src/model_evo_harness/provider.py#L11), [catalog/applicability](../../src/model_evo_harness/catalog.py#L287), and [experiment loop](../../src/model_evo_harness/engine.py#L254). The new manifest fields in this review make the boundaries machine-readable; they do **not** close the training gaps below. The TensorFlow counterparts were checked for the same public contract; this review did not reproduce numerical results from the upstream papers.

## Prioritized gap matrix

| **P0** | **Method availability is being confused with trainability.** The manifest names a class, and `model_api()` extracts AST signatures ([catalog.py](../../src/model_evo_harness/catalog.py#L45)); `run_search()` hands an arbitrary host candidate to `task.evaluate()` ([engine.py](../../src/model_evo_harness/engine.py#L368)). The framework has four small training helpers per backend ([PyTorch](../../src/model_evo_harness/models/pytorch/training.py#L11), [TensorFlow](../../src/model_evo_harness/models/tensorflow/training.py#L6)), but no generic trainer/recipe. By comparison, [FunRec YouTubeDNN](https://github.com/datawhalechina/fun-rec/blob/master/src/funrec/models/youtubednn.py) binds item table, sampled-softmax loss, and user/item evaluators; [Torch-RecHub MatchTrainer](https://github.com/datawhalechina/torch-rechub/blob/main/torch_rechub/trainers/match_trainer.py) binds mode, sampler, optimizer, early stopping and device. | A card can be `ready` while the Agent lacks a legal loss, candidate sampler, labels or scorer. It may repeatedly tune one host-supported MLP because a listed model cannot actually be trained in that host. | Add **two host-executable recipes first**: one tabular ranking/policy recipe and one retrieval/sequence recipe. Each recipe declares inputs, output kind, labels, loss, sampler, optimizer/steps, GPU/device, fixed evaluator and model import. Validate on a frozen full dataset; reject unsupported candidate configurations before spending an experiment step. Avoid copying an upstream trainer wholesale. |
| **P0** | **Paper scope was not machine-readable.** Previously a manifest entry only named ID/framework/symbol/file ([manifest](../../src/model_evo_harness/data/model_implementations.json#L1)); `method_applicability()` reported frameworks from that name alone ([catalog.py](../../src/model_evo_harness/catalog.py#L305)). This review adds `reference_scope`, `training_support`, `limitations` and `output_contract` to every entry. Several omissions are material: local [DIEN](../../src/model_evo_harness/models/pytorch/sequence.py#L205) lacks the auxiliary next-behavior objective described by [DeepCTR](https://deepctr-doc.readthedocs.io/en/latest/Features.html#dien-deep-interest-evolution-network); [MIND](../../src/model_evo_harness/models/pytorch/sequence.py#L36) has fixed K and no sampled-softmax path, unlike [FunRec MIND](https://github.com/datawhalechina/fun-rec/blob/master/src/funrec/models/mind.py); [DCNv2](../../src/model_evo_harness/models/pytorch/interactions.py#L237) has matrix/low-rank crosses, no expert mixture as in [DeepCTR DCNMix](https://github.com/shenweichen/DeepCTR/blob/master/deepctr/models/dcnmix.py). | An Agent can treat a compact core as a complete paper reproduction, attribute a null result to the *wrong* hypothesis, or compare incompatible outputs. | Feed these new fields through `model_api()` and proposal context. For each candidate, require the Agent to name **implemented mechanism**, **omitted mechanism**, **host trainer/loss**, and **output interpretation**. Test that a DIEN proposal cannot claim auxiliary-loss treatment without code supplied by the host. |
| **P1 for final claims** | **The exploratory champion and a validated improvement need distinct labels.** `_evaluation()` requires a finite `score` and arbitrary `metrics` dict ([engine.py](../../src/model_evo_harness/engine.py#L92)); a tiny directional improvement can change `best_id` ([engine.py](../../src/model_evo_harness/engine.py#L380)). This is useful for choosing the next experiment. `business_observations.uncertainty` is only checked as nonempty text ([engine.py](../../src/model_evo_harness/engine.py#L100)); the adapter assigns paired intervals and final holdout to the host ([adapter-contract.md](../adapter-contract.md#L37)). [CausalML validation](https://causalml.readthedocs.io/en/latest/validation.html) treats uncertainty as part of uplift comparison. | Repeatedly selecting the largest validation score can make its point estimate optimistic. Calling that score leader a reliable coupon-policy gain would overstate the evidence, especially when cost and incremental value are close. | Keep `best_id` as the exploratory validation score leader; do **not** require a confidence interval for each experimental promotion. Label it accordingly in reports. Before a final `validated_improvement` claim, require the host's protected final evaluation with prespecified net-value/uplift criterion, paired delta/interval at the correct randomization unit, and guardrails. Record the number of tried candidates and keep final-test access separate from the iterative search. |
| **P1** | **Input readiness is name/capability based, not schema/evidence based.** Snapshot validates `fields: list[str]` and `capabilities: list[str]` ([engine.py](../../src/model_evo_harness/engine.py#L44)); applicability checks membership in `requires` ([catalog.py](../../src/model_evo_harness/catalog.py#L287)). `feature_schema` is optional in docs ([adapter-contract.md](../adapter-contract.md#L39)); training-pattern `required_evidence` is prose ([training_patterns.json](../../src/model_evo_harness/data/training_patterns.json#L4)). [DeepCTR feature columns](https://deepctr-doc.readthedocs.io/en/latest/Features.html#feature-columns) explicitly separate sparse, dense and variable-length fields, vocabulary/embedding, length and weighting. | The Agent cannot safely choose FM vs sequence vs field-aware variants, verify pre-decision timing, or decide whether a hard-example pattern is justified from names alone. `ready` currently means *declared*, not *measured*. | Make typed field and label provenance a required host contract for relevant recipe families: type, shape/cardinality, missingness, time cutoff, mask/padding, item/candidate identity. Attach evidence IDs for observed residuals, learning curves, class support and slice diagnostics. A pattern is executable only when its evidence and recipe prerequisites are present; otherwise return `needs_contract`, not a new-feature request. |
| **P1** | **Retrieval training is underspecified.** [YouTubeDNN](../../src/model_evo_harness/models/pytorch/retrieval.py#L223) explicitly outputs scores on supplied candidates, not full sampled softmax; [YouTubeSBC](../../src/model_evo_harness/models/pytorch/retrieval.py#L262) subtracts supplied log sampling probability. `hard_negative_indices()` returns current-score top-K from a host eligibility mask ([training.py](../../src/model_evo_harness/models/pytorch/training.py#L37)); it does not create a random/hard mixture, false-negative filter, sampler probability log or full-catalog evaluator. Omitted auxiliary losses or session encoding may be the actual source of a paper's gain. | Keep the compact references; add recipe variants only when required data exists. First test DIEN extraction/evolution **with vs without** auxiliary next-event loss, then MIND fixed vs adaptive K and sampled objective, and DSIN session-bias ablation. | **P1** | **Loss/sampling/optimizer coverage is guidance-heavy.** There are 13 patterns ([training_patterns.json](../../src/model_evo_harness/data/training_patterns.json#L1)) and guides for [loss](../../src/model_evo_harness/knowledge/training_objectives.md#L1) and [hard examples](../../src/model_evo_harness/knowledge/sampling_and_hard_examples.md#L1), but only focal, BPR, one listwise CE and a top-K selector in [`training.py`](../../src/model_evo_harness/models/pytorch/training.py#L11). ## Recommended first two changes

1. **Wire the manifest boundaries into the Agent and enforce a typed candidate recipe.** A proposal should be able to select only a method variant whose actual input/output, label and host training dependencies are satisfied. Start with one full-data coupon ranking/uplift adapter and one retrieval adapter; compare to fixed baselines. This directly addresses the repeated micro-tuning failure mode.
2. **Separate exploratory ranking from final evidence.** Keep the directional validation `best_id` for Agent search and label it an exploratory champion. Let the host run one protected final comparison of the selected candidate against the prespecified baseline, with paired uncertainty and guardrails where the task needs them. The journal should still preserve inconclusive and failed trials as evidence; the next hypothesis should cite a measured residual, training symptom or business observation.

The next model-specific implementation should be chosen by an observed bottleneck. For sequence tasks with next-event labels, DIEN auxiliary training is the most direct fidelity gap; for retrieval with a full catalog, a sampled-softmax/in-batch-negative recipe may produce more useful experiments than another network block. Neither is a guaranteed gain.

## Audit limits

- The upstream comparison uses public source/docs, not a line-by-line formal verification of every paper or execution on each upstream project's datasets. The 44 local method cards are **not** the union of all DeepCTR and Torch-RecHub models.
- The local implementation inventory was changing concurrently. File/line references reflect the 2026-10-05 working tree at review time; rerun tests and regenerate digests before release.
- No claim of accuracy, uplift, policy value or business improvement follows from this audit or the new metadata. Those need host-run fixed-dataset experiments and valid uncertainty analysis.
