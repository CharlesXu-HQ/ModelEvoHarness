# DeepCTR and Torch-RecHub: incremental research map

Reviewed the official source and documentation at [DeepCTR `1b5fe40`](https://github.com/shenweichen/DeepCTR/tree/1b5fe40e158d1ee6af8b1d9df217a5ed5aea9136) and [Torch-RecHub `beb8b46`](https://github.com/datawhalechina/torch-rechub/tree/beb8b46fb718ce486ea5feb6847ac3abf0c491d4), against this harness's [38 FunRec method cards](../../src/model_evo_harness/data/method_cards.json) and [19 research families](../../src/model_evo_harness/data/catalog.json). “Absent” below means absent from the **current harness cards**, not that FunRec never mentions the subject. These are research hypotheses and task-adapter contracts, not claims of better accuracy or bundled implementations.

## Shortlist for the Agent loop

1. **Preflight from real feature metadata.** The host may declare categorical vocabulary/hash policy, dense dimensions, field grouping, variable-length maximum, padding/mask and shared embedding identity, plus candidate/history alignment. DeepCTR explicitly distinguishes `SparseFeat`, `DenseFeat` and `VarLenSparseFeat`, and the [sequence cookbook](https://github.com/shenweichen/DeepCTR/blob/1b5fe40e158d1ee6af8b1d9df217a5ed5aea9136/docs/source/Sequence-Cookbook.md) binds each prediction row to one target and one label. Harness inference: require histories strictly earlier than each target timestamp and learn encoders on training data only to prevent leakage. Missing metadata should yield `needs_data`, never invented readiness.
2. **Controlled cross architecture ladder.** On the same training/validation split and raw fields, compare vector DCN → matrix DCNv2 → low-rank expert mixture, holding parameter count or training/latency budget explicit. Track primary objective, rare-field slices and latency. Separately compare FM → field-pair weighting or input-conditioned field weights. A field-aware proposal needs actual categorical field identities and enough support; [DeepFFM's source](https://github.com/datawhalechina/torch-rechub/blob/beb8b46fb718ce486ea5feb6847ac3abf0c491d4/torch_rechub/models/ranking/deepffm.py) multiplies each field's embedding space by the number of fields, so memory is a failure signal.
3. **Session and negative-sampling protocol.** A session-retrieval task must expose ordered item events, session boundaries, target item IDs, item catalog, and an unchanged negative-sampling/candidate-universe definition. Compare mean history vs a single session model before adding more interests. Torch-RecHub has [uniform/popularity samplers](https://github.com/datawhalechina/torch-rechub/blob/beb8b46fb718ce486ea5feb6847ac3abf0c491d4/torch_rechub/utils/match.py) and [in-batch negatives](https://github.com/datawhalechina/torch-rechub/blob/beb8b46fb718ce486ea5feb6847ac3abf0c491d4/torch_rechub/trainers/match_trainer.py); harness inference: freeze sampler seed and IDs/digest, distinguish sampled-candidate metrics from full-catalog retrieval, check duplicate positives/false negatives before interpreting gains. When item sampling weights exist, [YouTubeSBC's source](https://github.com/datawhalechina/torch-rechub/blob/beb8b46fb718ce486ea5feb6847ac3abf0c491d4/torch_rechub/models/matching/youtube_sbc.py) supports a separate corrected-vs-uncorrected ablation. Its source constructor requires `sample_weight_feature`, `item_params` and `batch_size`; the [short docs example](https://github.com/datawhalechina/torch-rechub/blob/beb8b46fb718ce486ea5feb6847ac3abf0c491d4/docs/en/models/matching.md) omits them.
4. **Task-dependence test before AITM or loss balancing.** Require label definitions, order, coverage and missingness per task. Compare AITM's transfer to independent heads and MMoE/PLE on the same examples; report every task and the primary objective. Torch-RecHub also has [MetaBalance](https://github.com/datawhalechina/torch-rechub/blob/beb8b46fb718ce486ea5feb6847ac3abf0c491d4/torch_rechub/basic/metaoptimizer.py), which scales auxiliary gradients: treat optimizer choice as a *separate* ablation from architecture, and watch for degradation in the primary task.
5. **Reproducible comparison record.** Extend the host snapshot/journal with split ID, preprocessing digest, sampler and candidate universe, optimizer/seed/epochs, measured training and inference cost, per-task metrics, and source revisions. Torch-RecHub's [benchmark schema/runner](https://github.com/datawhalechina/torch-rechub/blob/beb8b46fb718ce486ea5feb6847ac3abf0c491d4/benchmarks/runner.py) demonstrate a fixed comparison protocol and metric-aware tolerance checks. Its benchmark is explicitly **experimental** and based on sample files ([design](https://github.com/datawhalechina/torch-rechub/blob/beb8b46fb718ce486ea5feb6847ac3abf0c491d4/benchmarks/BENCHMARK_DESIGN.md)); it is evidence for protocol design, not full-data performance claims. Task adapters retain ownership of actual metrics and final holdout.

## Boundaries

- DeepCTR is a TensorFlow/Keras implementation ([README](https://github.com/shenweichen/DeepCTR/blob/1b5fe40e158d1ee6af8b1d9df217a5ed5aea9136/README.md)); the portable part here is the hypothesis and data contract. Torch-RecHub is PyTorch, but the independent harness should keep model execution in the host adapter. No upstream model code is needed in this Apache-2.0 project.
- The [Torch-RecHub matching documentation](https://github.com/datawhalechina/torch-rechub/blob/beb8b46fb718ce486ea5feb6847ac3abf0c491d4/docs/en/models/matching.md) explicitly flags a current `GRU4Rec.forward()` listwise-axis issue. Do not recommend running that implementation unchanged; a host must validate it first.
- CouponEvo's fixed coupon dataset lacks item histories, item catalog, session boundaries and ordered CTR→CVR labels. These additions can improve the cross-scenario harness, but they must remain `needs_data`/`other_stage` in that consumer. Even field-interaction experiments are hypotheses; an out-of-sample metric and uncertainty interval decide whether they helped.
