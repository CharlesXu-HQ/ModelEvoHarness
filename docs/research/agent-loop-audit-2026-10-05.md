# Agent experiment-loop audit — 2026-10-05

Scope: the local working trees of **ModelEvoHarness** (`544badf` plus concurrent edits) and **CouponEvo** (`fbc13f0` plus concurrent edits), read on 2026-10-05. CouponEvo is the first host; the standalone harness also has its own generic runner. Line references below identify the observed code and may move before publication. “Observed” means the control flow is present in code; “risk” is the consequence inferred from that flow. This audit does not equate validation selection with final causal evidence.

## What is already connected

- **Observed:** CouponEvo evaluates a frozen seed, hands the Agent the dataset snapshot, catalog, applicable methods, step-level validation history, selected detailed reports, candidate code and dataset-bound lessons, then runs a proposed candidate and reflects on the result (`CouponEvo/src/couponevo/search.py:85-121, 266-349, 412-480`). Agent code can import catalog-declared PyTorch reference modules; execution remains behind the host evaluator (`search.py:172-203, 443-455`).
- **Observed:** The initial `model_api` signatures are now supplemented by bounded, on-demand complete source reads. `ModelEvoHarness/src/model_evo_harness/catalog.py:53-86` returns bundled module contents and SHA-256; `provider.py:13-52` permits at most two read rounds and records host-observed hashes. CouponEvo invokes that helper at `src/couponevo/agent.py:220-236` and saves the read record in `search.py:202-204, 425-426`. This closes the earlier “signature only” gap for the current integration; it does not prove every generated candidate will run.
- **Observed:** CouponEvo keeps validation separate from one-time final test evaluation. The validation report warns against interpreting repeated-selection intervals as final evidence (`src/couponevo/cli.py:345-365`), and finalization evaluates the frozen champion against the seed with paired bootstrap estimates (`src/couponevo/search.py:484-523`, `cli.py:406-418`). Exploration should continue to optimize **testable hypotheses and completed experiments**, without requiring a significant uplift at every trial.

## Remaining findings, ordered by effect on useful experiments

| Priority | Evidence and risk | Minimal repair and verification |
| --- | --- | --- |
| P1 — infrastructure failures consume hypotheses | **Observed:** the standalone runner catches *every* `task.evaluate` exception as a failed trial and stores only its exception class (`ModelEvoHarness/src/model_evo_harness/engine.py:373-397`). CouponEvo similarly marks any `_evaluate` exception `failed` and stores truncated stderr (`CouponEvo/src/couponevo/search.py:443-458`). **Risk:** a provider, filesystem, GPU or evaluator outage can consume `max_steps`, be reflected as a model failure, and give the Agent too little information for a targeted repair. | Let the host classify `candidate_failure` versus `infrastructure_failure`. Retry only transient infrastructure failures with the same trial ID and a small cap; preserve a bounded, credential-scrubbed diagnostic artifact. Count candidate failures as experiments, not service failures. Test one transient evaluator outage and one deterministic bad candidate. |
| P1 — generic proposal failure aborts the loop | **Observed:** standalone `agent.propose` or `_proposal` errors escape immediately (`engine.py:344-372`); HTTP/JSON failures are raised from `provider.py:168-200`. CouponEvo corrects invalid proposal **contracts** once (`CouponEvo/src/couponevo/search.py:358-375`), but provider transport errors still escape. **Risk:** one malformed response or transient API failure ends a search before a trial is attempted. | Retry bounded transport/parse errors without allocating a trial, and return validation errors to the Agent as correction context. Persist a sanitized attempt count and terminal failure reason. Test one recoverable malformed response and a two-failure cap. This is a reliability gate, not a requirement for a positive metric. |
| P1 — replayed quantitative lessons can be misleading | **Observed:** CouponEvo filters prior searches by dataset, manifest, objective, budget, seed, framework and harness (`src/couponevo/experience.py:9-29`), but not `initial_candidate`, `device` or `sandbox_image`, although the task records them (`search.py:207-223`). It replays `validation_delta` against each old seed (`experience.py:29-45`); business replay retains an observation ID and prose but drops the observed metric, estimate and uncertainty (`experience.py:46-59`). **Risk:** a delta from a different baseline or execution environment can be treated as comparable, and an old business insight cannot be checked against its numeric evidence in the new prompt. | Keep qualitative same-dataset lessons, but attach baseline candidate and execution provenance; replay numeric deltas only where the comparison protocol matches. Include the cited aggregate observation and uncertainty beside each business insight. Test changed baseline/device and observation replay. |
| P2 — terminal budget record obscures remaining ideas | **Observed:** after `max_steps`, CouponEvo asks for one terminal decision; if the Agent still proposes an experiment, it saves `budget_exhausted_decision.reason = "no_terminal_action"` and stops (`src/couponevo/search.py:350-383`). A later resume with a larger step limit is possible; the journal nevertheless loses the proposed next hypothesis. **Risk:** reports can imply a decision failure or exhausted idea space when only the configured trial budget ended. | Save `status=budget_limit` and the rejected next proposal's **research metadata only** (no new candidate execution), plus remaining-budget context. Verify a valid next hypothesis survives the limit and becomes visible on resume. |
| P2 — custom adapters can assert a reference read | **Observed:** the built-in provider replaces Agent-supplied `reference_reads` with host-computed hashes (`ModelEvoHarness/src/model_evo_harness/provider.py:37-43`), but the generic runner's `_proposal` copies that field from any custom `agent.propose` result (`engine.py:223-228`). CouponEvo's generic proposal path also copies it (`CouponEvo/src/couponevo/search.py:202-204`). **Risk:** a third-party adapter can journal a hash without making a host-observed read. | Treat read provenance as host runtime state, not proposal data. Have custom adapters use the shared read helper or omit the field; accept hashes only from a host-owned read ledger. Test an injected fake hash is not recorded as a read. |
| P2 — business claim evidence is referential, not semantic | **Observed:** business observations are policy-level validation aggregates (`CouponEvo/src/couponevo/harness.py:242-272`). Reflection validation checks that `observation_id` exists and insight/limitations are nonempty (`harness.py:275-297`); standalone validation does the same (`ModelEvoHarness/src/model_evo_harness/engine.py:160-181`). **Risk:** free text can still claim a cohort effect or causal mechanism not represented by the aggregate ID. The prompts prohibit this, but the validator cannot prove the text follows the metric. | Persist an evaluator-generated structured claim tuple (population, metric, estimate, uncertainty, holdout) with the cited observation. Treat prose as interpretation and mark unsupported subgroup or causal claims for review. A test should reject a claimed subgroup when only whole-policy observations exist. |
| P2 — an Agent may stop with little exploration evidence | **Observed:** CouponEvo accepts any nonempty stop reason (`src/couponevo/search.py:146-151, 384-388`); the generic runner does likewise (`ModelEvoHarness/src/model_evo_harness/engine.py:348-356`). CouponEvo's prompt asks why other mechanisms lack a testable hypothesis, but there is no structured record. **Risk:** a baseline-only stop can be indistinguishable from a considered no-op decision. | Require a short `stop_basis` and one concrete next hypothesis considered/rejected for an ordinary stop; allow explicit budget or host-constraint stops. Do not mandate more trials solely for statistical significance. Test a baseline-only unsupported stop and an explicit host blocker. |

### Fixed during this audit

- CouponEvo previously accepted a `feature_request` for an already-present field and accepted a `domain_requirement` with a different `source` or `as_of`. `src/couponevo/harness.py:207-239` now requires absence and exact host provenance, matching the standalone contract in `ModelEvoHarness/src/model_evo_harness/engine.py:119-157`. The new integration test first reproduced all three failures; `tests/test_model_evo_integration.py` passes with the submodule package.
- A transient analyzer error formerly made an evaluated CouponEvo candidate permanently ineligible. `src/couponevo/search.py:459-480` now retries analysis once against the **same saved evaluation**, records `analysis_attempts`, and clears `analysis_error` on success. The new `tests/test_search.py` case confirms no extra `_evaluate` call. Two failures still block promotion; manual repair or a later resumable analysis operation remains a future design choice. This preserves the holdout boundary.

### Data-request timing and selection discipline

The existing data-request gate is directionally correct: experimental requests cite two completed trials with distinct mechanisms, while immediate requests need an explicit host domain requirement (`CouponEvo/src/couponevo/harness.py:207-239`; `ModelEvoHarness/src/model_evo_harness/engine.py:119-157`). The remaining **inference** risk is that two unrelated experiments and free-text “evidence” may pass without establishing why the named absent field blocks progress. Keep the two-trial rule as a floor, then require the request to cite the *specific measured failure mode* and relevant alternatives tried; do not demand two statistically positive results. If a domain expert provides a predeclared requirement, keep the immediate route.

Validation winner selection is intentionally exploratory. CouponEvo promotes by the fixed validation objective after review (`src/couponevo/search.py:334-343, 465-479`) and reserves a separate final test (`search.py:484-523`). Repeated search can make the winner's validation point estimate optimistic; this is a reporting and final-evaluation concern, **not** a reason to gate each hypothesis by confidence interval. Report the number of tried candidates beside the champion and keep final test access one-time.

## Upstream mechanisms actually consulted

- [autoresearch `program.md`](https://github.com/karpathy/autoresearch/blob/master/program.md) keeps data/evaluation fixed while the Agent edits the training script; it records keep/discard/crash and explicitly reads a crash traceback before debugging. The transferable mechanism is a high-throughput, inspectable trial ledger and useful failure feedback. Its language-model validation metric does not establish an uplift inference protocol.
- [OpenRSI OpenMLE-Evo usage guide](https://github.com/FrontisAI/OpenRSI/blob/main/OpenMLE-Evo/docs/usage.md) documents a separately scored sandbox result, transient retries using the same attempt ID, single-writer journal/checkpoint updates and strict resume. Those details support retrying infrastructure without charging another research attempt; they do not imply this project should train the Agent itself.
- [LegoFlow README](https://github.com/LegoX/LegoFlow) separates task curation, trajectory capture, training and evaluation, and describes setup/check/run plus archived artifacts for each block. For this project, the useful boundary is a host-owned evaluator and auditable attempt artifacts; copying all four blocks would add an Agent-training scope the current task does not require.
