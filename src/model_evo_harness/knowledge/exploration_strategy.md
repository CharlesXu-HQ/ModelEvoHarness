# Choosing the next experiment

This guide helps an Agent spend a small experiment budget on informative tests. It is **not** a model checklist: start from a measured failure, consider mechanisms inside or outside the catalog, and choose one test that could change the next decision. A `ready` card means declared inputs exist, not that the method is promising. The host still owns feature construction, training, evaluation, costs, and the final holdout.

## First establish the comparison

Record the decision stage, eligible population, target, training label provenance, fixed validation units, candidate universe, metric denominator and K, temporal cutoff, and deployment constraints. For implicit feedback, distinguish an observed negative from an unobserved sampled item. RecBole explicitly separates full-catalog, uniform-sampled, popularity-sampled, and labeled evaluation, and keeps training sampling in a separate setting ([evaluation](https://recbole.io/docs/user_guide/config/evaluation_settings.html), [training](https://recbole.io/docs/user_guide/config/training_settings.html)). A different evaluation mode or population is a new protocol, not an improvement over the old score.

Before proposing, read the baseline and prior trials for one supported symptom: loss curves, per-unit errors, user/item support, history length, popularity, calibration, cohort response, action rate, budget use, or latency. If that evidence is absent, request a **diagnostic report using existing data** from the host adapter; do not invent a cause or demand a new feature field. Preserve the host's pre-decision feature boundary.

Spend trials for information: when an inexpensive check of input shape, label semantics, score meaning, policy overlap, or a one-component ablation can reject a hypothesis, do that before trying another architecture. Cite host-observed facts separately from declared metadata and the Agent's interpretation. A list of intended code changes cannot verify what the executed candidate changed; use the host's implementation check and change audit when recording mechanism experience.

Before claiming that a proposed structure adds expressive power, trace the parent code's prediction or score function and the candidate's function. Write the input-dependent term or interaction that is genuinely new **and reaches the score or action used by the fixed metric**. More parameters, another head, or a different class name do not establish this. If the code path cannot be derived from the available source and runtime facts, mark the claim unverified and ask for a small diagnostic. Keep a change to the metric-driving prediction or decision separate from a change that only adds output fields, logs, or diagnostics. For the latter, first check the output contract and shapes using an inexpensive adapter check; it is not an optimization-effect trial or a useful performance ablation while the score and action are unchanged.

## Diagnostic paths

These are conditional examples, not an exhaustive or required sequence. `Reference` means the repository has a local model core for at least part of the mechanism; `design` means the idea is guidance until an adapter or independent implementation supplies it.

| Measured symptom → mechanism | Data required | Smallest useful control | Reject the hypothesis when | Current boundary |
| --- | --- | --- | --- | --- |
| Sparse user/item histories have a stable recall gap despite ID factorization → test interaction-graph propagation; if graph perturbations are meaningful, separately test a self-supervised view loss. | Training-period user–item graph, stable IDs, timestamps, fixed catalog and eligible top-K. | Compare ItemCF or factorization, then graph propagation at matched dimensions/K; only after a graph gain, ablate the extra self-supervised loss. | Gain vanishes on temporal or tail slices, shuffled edges perform similarly, or graph construction uses future interactions. | ItemCF/factors: reference. LightGCN-style propagation and SGL-style contrastive views: design; new model and host graph builder needed. [RecBole LightGCN](https://github.com/RUCAIBox/RecBole/blob/master/recbole/model/general_recommender/lightgcn.py), [SGL](https://github.com/RUCAIBox/RecBole/blob/master/recbole/model/general_recommender/sgl.py). |
| Cold items remain invisible after ID/co-occurrence tests, and real entity relations could connect them → test typed knowledge-side information. | Training-cutoff item–entity links, entity/relation triples, item attributes and link coverage by cold status. | Compare side-attribute or EGES retrieval with one relation-aware representation at the same candidate budget; ablate links and relation types separately. | Improvement follows future links, a larger candidate pool, or entity popularity rather than relations. | EGES: reference. Typed KG retrieval: design; graph/joins and model adapter needed. [RecBole atomic-file roles](https://recbole.io/docs/user_guide/data/atomic_files.html). |
| One recall channel misses distinct supported intents, while adding capacity to that channel does not recover them → test candidate-channel composition. | Per-channel candidate IDs and scores, eligibility, deduplication, final K, and an unchanged downstream ranker. | Compare the best single channel with a two-channel union at the **same total K** and same ranker; then inspect unique relevant items and overlap. | Apparent gain is only a larger candidate budget, duplicates, stale inventory, or later-stage regression. | Design plus retrieval adapter; Wang's [other recall channels](https://github.com/wangshusen/RecommenderSystem/blob/main/README.md) motivates the system question, not an automatic gain. |
| Recent-N history misses long-term interests, but scanning all history is costly → test a cheap relevance filter before target-aware sequence encoding. | Timestamped pre-decision events, candidate representation, long-history coverage, and a serving-cost bound. | Keep the same candidate and scorer; compare recent-N, same-size target-relevant history, and a shuffled-selection control. | Improvement disappears under strict cutoff or comes only from longer input/greater compute. | DIN/DIEN references exist; a two-stage long-history selector is design and needs adapter support. Wang lists [SIM and sequence topics](https://github.com/wangshusen/RecommenderSystem/blob/main/README.md). |
| Sampled retrieval training is easy but full-catalog recall or tail coverage is weak → vary the **training sampler**, not the evaluator. | Positive interactions, eligible item catalog, negative provenance, sampler probabilities if correction is proposed, stage-specific labels, fixed evaluation universe. | Compare random or in-batch sampling with one bounded hard-negative mixture at equal count, model, steps and catalog; separately test logit correction when actual sampling probabilities exist. | Full-catalog metric/coverage falls, mined items are plausible positives, or a gain exists only on the training sampler's candidate set. | Sampling helpers and YouTubeSBC reference exist; stage-specific pool construction and false-negative audit belong to the adapter. RecBole [label semantics](https://recbole.io/docs/user_guide/data/label_of_data.html), [sampler settings](https://recbole.io/docs/user_guide/config/training_settings.html), Wang's [retrieval-negative lesson](https://github.com/wangshusen/RecommenderSystem/blob/main/Slides/02_Retrieval_07.pdf). |
| Prediction metrics hold but business utility, calibration or a guardrail is weak → keep predictions fixed and test the action rule or calibrated mapping. | Frozen per-action predictions, eligibility, calibrated outcome/cost definitions, budget or slate constraints, and a valid off-policy or randomized evaluator where needed. | Compare current rule with one declared threshold, value fusion or feasible-set rule on the same scored units; measure action rate, cost and utility separately. | Gains rely on changing the predictor simultaneously, violate feasibility, or lack support for the policy-value estimand. | Decision guide exists; optimizer and evaluator are adapter responsibilities. Wang lists [score fusion](https://github.com/wangshusen/RecommenderSystem/blob/main/Slides/03_Rank_03.pdf); the local [decision mapping guide](decision_mapping.md) defines coupon boundaries. |
| A predeclared sparse cohort has repeatable calibration error while the pooled model ranks reasonably → test small cohort calibration or residual correction before a separate network. | Pre-decision cohort membership, support/effective sample size, untouched calibration rows and a common validation objective. | Freeze pooled predictions; compare global calibration with one shrinkage-controlled cohort correction at identical rows and score rule. | Gain disappears under unit-level uncertainty, worsens the primary objective, or the cohort is chosen using validation labels. | Design plus calibration adapter; multi-scenario network references exist but do not establish this correction. Wang's [special-population material](https://github.com/wangshusen/RecommenderSystem/blob/main/README.md). |
| Pointwise sort yields poor slate utility or violates placement rules → add a **feasibility filter** before testing diversity-aware reranking. | Logged eligible slates, positions, item attributes, hard business rules, a similarity signal, and slate-level evaluation support. | Compare score sort with a rule-feasible greedy order at fixed slate size; only then add one diversity term on the same feasible set. | The rule cannot be checked offline, the candidate pool changes, or reward gains are artifacts of unobserved position effects. | PRM/PRS are references; rule-feasible MMR/DPP and unbiased slate evaluation require adapter work. Wang's [reranking notes](https://raw.githubusercontent.com/wangshusen/RecommenderSystem/main/Notes/06_Rerank.pdf). |
| A model family appears better only after a much larger search or training budget → test a matched baseline and one bounded parameter axis. | Search-space bounds, optimizer/seed/epochs, resource use, fixed split and validation metric. | Tune the simpler baseline with the same budget, then change exactly one structural or loss mechanism and compare paired runs. | The gain disappears at matched compute or across independent seeds/units. | Training-pattern guidance exists; search scheduling and uncertainty are host responsibilities. RecBole separates [fixed configuration and parameter spaces](https://recbole.io/docs/user_guide/usage/parameter_tuning.html) and documents [baseline comparison](https://recbole.io/docs/user_guide/usage/significance_test.html). |

For retrieval, **exposed but unclicked** is an observed non-click, not automatically a sound hard negative for a broad recall objective. It can train a different ranking target, while coarse-rank rejects or mined eligible items may test the recall boundary. Decide from the target and logging process; compare random/in-batch/hard mixtures under the same full-catalog evaluator. Likewise, a randomized coupon non-response is not a negative treatment effect. The local [sampling guide](sampling_and_hard_examples.md) gives further controls.

## Close the loop without inventing certainty

Write one falsifiable mechanism, an unchanged control, required data and a rejection signal. A failed experiment should narrow the next hypothesis; a metric improvement alone does not prove the mechanism or business cause. The journal's best validation score is an **exploratory champion**. Ask the host for paired uncertainty, guardrail checks and a separately protected final holdout before describing a candidate as independently validated. RecBole's [significance-test workflow](https://recbole.io/docs/user_guide/usage/significance_test.html) is a comparison example, not a substitute for the host's correct unit and estimator.

In reflection, correct premises contradicted by parent-code algebra or observed execution before recording technical experience. State which terms actually feed the evaluated score, which changes only improve observability, and which parts remain unverified. Do not suggest a performance ablation that only toggles an extra reporting field; use a cheap contract check, then return to a hypothesis that could change the prediction or decision.

A confidence interval that crosses zero does not establish equivalence, nor does a narrower policy-effect interval by itself show that a model's treatment-effect predictions have lower variance. Distinct policies can have the same aggregate estimate; inspect selected-unit identities and paired contributions before calling this an evaluation anomaly.

If several distinct mechanisms fail and the same unsupported residual remains, propose a specific human feature request with its source, pre-decision timestamp and validation plan. An explicit host business requirement can justify that request immediately. Keep technical experience (what a mechanism did) separate from observed business experience (what a defined population did), and cite only host-supplied observations for the latter.

## Source and scope

This text is independently written from [RecBole's current documentation and model sources](https://recbole.io/docs/) and [Wang Shusen's lecture index](https://github.com/wangshusen/RecommenderSystem). It borrows research questions, not code or prose. The examples above do not make the harness a complete recommender, search, ad-auction or coupon-policy system. In particular, a fixed coupon RCT usually has neither an item graph, long item history nor slate; those directions remain inapplicable until an adapter declares and verifies their inputs.
